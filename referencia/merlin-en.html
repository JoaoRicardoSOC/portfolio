The problem

A Leroy Merlin store can reach 10,000 square meters, with thousands of technical products and shoppers ranging from the curious to professional builders. The FIAP challenge was to improve that in-store journey using AI. Leroy Merlin mapped three pain points:

The last meter

Finding the exact shelf in a layout full of aisles and categories.

Vocabulary

Shoppers don’t know the technical name of what they need, and the knowledge stays with the staff.

Empty shelf

A product runs out on the shelf, nobody notices, and the purchase is abandoned.

The pivot

The first version had a kiosk at the entrance, an algorithm-computed route, and a JWT token to hand the session from the kiosk to the phone. In the August 24 mentoring session with Leroy Merlin, two guidelines simplified everything.

Before mentoring

  • Physical kiosk at the store entrance
  • Fixed route (Nearest Neighbor + 2-opt)
  • Single-use JWT handoff
  • Two devices for one journey
→

After mentoring

  • QR codes on the aisle columns
  • The shopper’s own phone, nothing to install
  • The map shows where they are and where each item is
  • Shoppers choose their own path, so impulse buying stays alive

Throwing away the kiosk, route and handoff we had already built hurt, but it brought the product much closer to the real world. The old reasoning stayed in the repository, because changing our minds is part of how we defend the project.

The solution

A mobile web app, opened straight from the camera. The journey has four moments:

  1. Scan the column

    The aisle QR code opens the app already knowing where the shopper is. No login, no download.

  2. Search the way you talk

    Search tolerates typos and missing accents, using UTL_MATCH and Jaro-Winkler inside Oracle itself.

  3. See it on the map

    A vector map of the store shows the shopper’s position and every item on their list.

  4. Ask or report

    The assistant answers DIY questions. An empty shelf turns into an in-stock substitute, one tap away.

For the store, every empty-shelf report becomes a database record: an ongoing list of where system inventory doesn’t match the shelf, coming from whoever is looking at it.

A change midway. The back end was born in Spring Boot with hexagonal architecture: a framework-free domain, ports and adapters. In November, the team decided to rewrite it to follow the course’s stack to the letter (JAX-RS, JDBC with DAO, no Spring). The rule was no regressions, and it was measured: the same routes before and after, with 195 tests in the default suite and 351 in the integration suite passing against Oracle.

Technical decisions

Four problems that took more than writing code. The team logged about 100 decisions in the repository, each with context, alternatives and cost.

AI without hallucination

The model chooses, but the database answers

The stockout flow is the heart of the demo, and the place where an AI inventing products would be fatal. The solution has three stages, each one constraining the next.

The model’s text never reaches the shopper raw: only the justification survives, and the product delivered is always the object from our own database. One test has the model answer with a made-up SKU, and checks that the shopper receives a different product.

If no candidate does the same job, the answer is "none fits", not just any product. Suggesting a circuit breaker to someone looking for sandpaper is worse than suggesting nothing.

Measure before choosing

The most expensive model was the worst for this job

The obvious choice was the top model. Integration tests showed the opposite: it reasons before answering, takes more than 20 seconds, and the free tier allowed 20 calls a day.

To pick a product from a list we provide, that reasoning adds nothing. Flash-Lite answers in about 1 second. The assistant’s tool also started accepting several terms in a single call: "what do I need to paint?" dropped from four round trips to the provider to two.

Performance

A hand-written connection pool

Without Spring, the connection pool went away too, and routes became 2 to 3 times slower in production. Measuring showed why: opening an Oracle connection cost about 230 ms, the equivalent of eleven queries, and from the US server it took over 1 second.

Since the migration rule banned libraries outside the course, the pool was written in plain Java, respecting the 20-session limit of FIAP’s database: idle connections close after 5 minutes, none lives longer than 25, and stale ones are tested before use. It ended up faster than the original Spring version.

Prove before fixing

The bug that didn’t exist

In a code review, saving the shopping list seemed to lose data when two requests touched it at the same time. The dangerous mechanism really existed. The team’s rule was: prove the fix improves something, or admit it’s a placebo.

The fix was implemented and then reverted: it changed nothing observable and introduced a bug of its own. What remained were five tests that lock in the verified behavior.

  • Repository probes lost data, but in empty transactions that no real use case produces
  • Concurrent threads passed with and without the change. A race is not reproducible proof
  • Counting written rows: 1 update on both sides, with 3 items or with 8
  • Forced staleness in a test-controlled transaction: nothing is lost. The system was already correct

Lessons

What we recorded as lessons, and what I would do differently.

  1. Reading code is not demonstrating a bug

    An elegant fix for a nonexistent problem almost made it into the repository, along with a well-written justification. Requiring proof is what separates engineering from opinion.

  2. Measure production before migrating

    The JAX-RS migration was validated on routes and tests, but the cost of opening database connections only showed up later, in production. Today I would measure real latency before removing the pool, not after.

  3. A green suite that hides what it skipped is misleading

    The default suite once showed "150 tests, 0 failures" while 8 integration tests were failing outside it. I would set up continuous integration running the full suite from day one.

  4. When the code doesn’t know, it should say so

    The same pattern showed up five times: the code invented a plausible value instead of admitting it didn’t know (the session, the position, the AI’s answer). The rule we kept was to fail loudly and show the shopper what happened.
